# SogouEdu 嵌套取货响应修复设计

## 问题

订单 `67600` 的取货接口返回 `data.payload.accounts`。现有编排只去掉最外层
`data`，随后把仍包含 `order/status/payload` 的包装对象交给账号解析器，导致 10
个有效账号被识别为 0 个。订单状态又已写成 `taken`，后续循环不再重新取货，
因而持续进入 `push_waiting`。

该订单的首次凭据和补发凭据已经人工导入号池，修复后不得回放订单内容。

## 处理方案

1. 增加交付载荷解包函数，有限深度处理 `data`、`payload` 包装，直到找到
   `accounts` 列表；同时兼容原有 `data.accounts`、顶层 `accounts` 和列表格式。
2. 取货成功后只保存解包后的账号载荷，避免状态文件继续持有无关包装层。
3. 对历史状态中的包装载荷，在推送前再次解包，保证服务升级后能够恢复旧订单。
4. 如果解包后仍没有有效账号，清除缓存载荷并把订单恢复为 `ready`，下一轮重新
   查询状态并调用取货接口；保留错误信息，不创建新订单。
5. 部署前停止服务，将 `67600` 记录为 `manually_completed` 并清除
   `current_order`，从而避免已人工导入的账号被重复推送。
6. 补发认领使用同一个解包函数，兼容 `data.payload.accounts`；仅处理
   `claimable`、`ready`、`available` 或显式带 `claim_url` 的记录，避免对
   `delivered` 历史记录重复认领。每轮从最新 recoveries 页开始，并合并本地
   待处理记录；`next_before_id` 仅用于审计，不作为下一轮扫描起点。

## 测试

- 真实形态 `data.payload.accounts` 能解析并推送一次；
- 成功后清除 `current_order`，不重复下单；
- 空交付载荷不会推送，会清除缓存并保持原订单等待下一轮重新取货；
- 保留原有单层响应测试，确保向后兼容。
- 嵌套补发认领能够更新原号，空补发不标记成功，已交付历史记录不会 claim。
